# Lucuma deployment shapes (odb / SSO / ITC / Explore)

**Research date:** 2026-08-14. Sources: `main` branches of `gemini-hlsw/lucuma-odb` and `gemini-hlsw/lucuma-apps`.

**Summary.** The whole backend (ODB, SSO, ITC, plus obscalc/calibrations/resource workers) now lives in the single monorepo [`gemini-hlsw/lucuma-odb`](https://github.com/gemini-hlsw/lucuma-odb) — the old `gemini-hlsw/lucuma-sso` repo is **archived** and SSO is `modules/sso-service` inside lucuma-odb. Docker images are built with sbt-native-packager on every push to `main` and pushed **only to Heroku's private container registry** (`registry.heroku.com/<app>-{dev,staging,production}/<proc>`, tagged with the git SHA plus `latest` for the `-dev` apps) — there is **no public image on Docker Hub or GHCR**, so an ephemeral CI stack must either build the images itself (`sbt <proj>/docker:publishLocal`, cheap-ish but a full Scala build) or pull from `registry.heroku.com` with a Heroku API key. Database migrations are **Flyway, run automatically at service startup** (skippable with `--skip-migration`); the repo also ships a `docker-compose.yml` + `docker-init/` scripts that stand up a single SSL-enabled Postgres 15 with both the ODB and SSO databases pre-migrated via raw `psql`, which is exactly what the repo's own CI uses. Explore is **not a container at all**: it lives in [`gemini-hlsw/lucuma-apps`](https://github.com/gemini-hlsw/lucuma-apps) under `explore/`, is built in GitHub Actions (Scala.js + Vite) and deployed as a static bundle to Firebase Hosting; it selects its backend **at runtime** by fetching `/environments.conf.json` and matching on the browser hostname (with a `"*"` fallback), so pointing it at a throwaway ODB/SSO is just a matter of serving the bundle with a custom conf file. SSO exposes a browserless JWT path: `POST /api/v1/auth-as-guest` needs **no credentials** and returns a JWT (10-minute lifetime), and API-key exchange (`GET /api/v1/exchange-api-key?key=…`, 3-hour JWTs) works for standard users given a service JWT minted with the `create-service-user` CLI subcommand — ORCID is only required for the interactive standard-user login flow.

## 1. lucuma-odb (backend monorepo)

Repo: <https://github.com/gemini-hlsw/lucuma-odb> (public, active). Contains ODB, SSO, ITC, and worker services; see [`ODB-README.md`](https://github.com/gemini-hlsw/lucuma-odb/blob/main/ODB-README.md), [`SSO-README.md`](https://github.com/gemini-hlsw/lucuma-odb/blob/main/SSO-README.md), [`ITC-README.md`](https://github.com/gemini-hlsw/lucuma-odb/blob/main/ITC-README.md).

### 1.1 Docker images and registry

From the `deploy` job of [`.github/workflows/ci.yml`](https://github.com/gemini-hlsw/lucuma-odb/blob/main/.github/workflows/ci.yml) (generated by sbt-github-actions; source of truth is [`build.sbt`](https://github.com/gemini-hlsw/lucuma-odb/blob/main/build.sbt) around lines 189–290):

- Runs only on push to `main` in the `gemini-*` org. Builds six images locally with sbt-native-packager (`LucumaDockerPlugin` + `JavaAppPackaging`):
  - `noirlab/lucuma-sso-service` (port 8082)
  - `noirlab/lucuma-itc-service` (port 6060)
  - `noirlab/lucuma-odb-service` (port 8082)
  - `noirlab/obscalc-service`, `noirlab/calibrations-service` (background workers, share the ODB Heroku app as `obscalc` / `calibration` process types)
  - `noirlab/lucuma-resource-service` (port 8484)
- Pushes each image to **`registry.heroku.com`** for the `-dev`, `-staging`, `-production` Heroku apps (`lucuma-sso-*`, `itc-*`, `lucuma-postgres-odb-*`, `lucuma-resource-*`), tagged `:<git-sha>`; the `-dev` variant is *also* pushed untagged (i.e. `:latest`), and only `-dev` is auto-released (`heroku container:release`). Staging/production get the SHA-tagged image for later manual promotion.
- **Tag tracking main:** effectively `registry.heroku.com/lucuma-postgres-odb-dev/web:latest` (and siblings), updated on every main push. Pulling requires Heroku registry auth (`docker login registry.heroku.com -u _ -p $HEROKU_API_KEY`) and collaborator access to those apps.
- **No public registry:** Docker Hub org `noirlab` publicly contains only `gemconda` (checked via `hub.docker.com/v2/repositories/noirlab/`). No GHCR publishing appears anywhere in the workflows. (Contrast: `lucuma-apps` *does* `docker login` to Docker Hub as `nlsoftware` for the observe/navigate images `noirlab/gpp-obs` etc. — but those are not the ODB stack, and they are not publicly listed either, so likely private Hub repos.)
- The only Dockerfile in the repo, [`modules/service/src/Dockerfile`](https://github.com/gemini-hlsw/lucuma-odb/blob/main/modules/service/src/Dockerfile), is **not** the service image — it builds a Postgres 15 image with ODB migrations pre-applied, for testcontainers.

Reproducing the images in CI is one command: `sbt ssoService/docker:publishLocal itcService/docker:publishLocal service/docker:publishLocal` (CI uses `-J-Xmx6g`, Java temurin@25, Scala 3.8.4, and the checkout needs **git-lfs** — CI uses `nschloe/action-cached-lfs-checkout`).

### 1.2 ODB boot configuration (env vars)

From [`modules/service/src/main/scala/lucuma/odb/Config.scala`](https://github.com/gemini-hlsw/lucuma-odb/blob/main/modules/service/src/main/scala/lucuma/odb/Config.scala) (all read via ciris `envOrProp`, i.e. env var or system property):

| Variable | Required | Notes |
|---|---|---|
| `PORT` | yes | HTTP port (Heroku convention) |
| `DATABASE_URL` | yes | Heroku-style `postgres://user:pass@host:port/db` |
| `ODB_SSO_ROOT` | yes | SSO root URI |
| `ODB_SSO_PUBLIC_KEY` | yes | GPG ASCII-armored public key used to verify JWTs (no fetch-from-SSO fallback) |
| `ODB_SERVICE_JWT` | yes | Service-user JWT (ODB calls SSO to exchange API keys) |
| `ODB_ITC_ROOT` | yes | ITC service root (polled every `ODB_ITC_POLL_PERIOD`, default 5 min) |
| `ODB_TELLURIC_ROOT` | no | defaults to `https://telluric-targets.gpp.gemini.edu/` |
| `ODB_DOMAIN` | yes | list of domains for CORS |
| `CORS_OVER_HTTPS` | no | default `true` — set `false` for a plain-HTTP throwaway stack |
| `CLOUDCUBE_ACCESS_KEY_ID`, `CLOUDCUBE_SECRET_ACCESS_KEY`, `CLOUDCUBE_URL`, `FILE_UPLOAD_MAX_MB` | yes | S3 (Cloudcube addon). Per ODB-README, **any dummy string works locally** (`CLOUDCUBE_URL` must be a URL, e.g. `https://cube.example.com/lucuma-staging`) |
| `MAILGUN_API_KEY`, `MAILGUN_DOMAIN`, `MAILGUN_WEBHOOK_SIGNING_KEY`, `INVITATION_SENDER_EMAIL`, `EXPLORE_URL` | yes | Mailgun; dummy values fine locally per README |
| `PROPOSAL_EMAIL_DEFAULT` (and per-type `PROPOSAL_EMAIL_*`) | yes (default var) | config load fails if unset |
| `ODB_OTEL_ENDPOINT`, `ODB_OTEL_KEY` | no* | OpenTelemetry/Grafana; no-op when unset **unless** `ODB_ENVIRONMENT` is non-local, in which case both are required |
| `ODB_ENVIRONMENT` | no | `local` (default) / `dev` / `staging` / `production` |
| `ODB_MAX_CONNECTIONS`, `OBSCALC_*`, `CALIBRATIONS_*`, `GOA_USER_IDS`, `HTTP_CLIENT_TIMEOUT`, `ODB_SLOW_QUERY_THRESHOLD_MS`, … | no | sensible defaults |

**Honeycomb is gone from ODB** (it now uses OTLP via `ODB_OTEL_*`); SSO still has an optional `HoneycombConfig`.

### 1.3 Migrations

- Flyway migrations live in [`modules/service/src/main/resources/db/migration/`](https://github.com/gemini-hlsw/lucuma-odb/tree/main/modules/service/src/main/resources/db/migration) (900+ `V*.sql` files) and **run automatically at startup**: [`Main.scala`](https://github.com/gemini-hlsw/lucuma-odb/blob/main/modules/service/src/main/scala/lucuma/odb/Main.scala) `migrateDatabase` (Flyway over JDBC) runs unless the `serve` subcommand gets `--skip-migration`; `--reset` drops and recreates the DB first.
- Same pattern for SSO ([`modules/sso-service/src/main/scala/Main.scala`](https://github.com/gemini-hlsw/lucuma-odb/blob/main/modules/sso-service/src/main/scala/Main.scala), migrations in `modules/sso-service/src/main/resources/db/migration/`).
- **Gotcha:** the repo's `docker-compose.yml` applies the same SQL via raw `psql` at initdb time (no Flyway history table), so a service booted against a compose-initialized DB **fails Flyway validation** unless you drop/recreate the DB or pass `--skip-migration`. For an ephemeral stack pick one mechanism: empty Postgres + let the services Flyway-migrate (simplest), or compose-init + `--skip-migration`.
- **SSL gotcha:** Flyway connects with `jdbc:postgresql://…?sslmode=require` ([Config.scala L185](https://github.com/gemini-hlsw/lucuma-odb/blob/main/modules/service/src/main/scala/lucuma/odb/Config.scala)), so **Postgres must have SSL enabled** (compose runs `postgres:15` with `-c ssl=on` and the repo's `test-cert/` server cert/key; cert files need `chmod 600` + `chown 999`). The Skunk pool itself uses `SSL.Trusted.withFallback(true)`.

## 2. SSO service

Lives in lucuma-odb at [`modules/sso-service/`](https://github.com/gemini-hlsw/lucuma-odb/tree/main/modules/sso-service). The standalone repo <https://github.com/gemini-hlsw/lucuma-sso> is **archived**. Containerized as `noirlab/lucuma-sso-service` (same sbt docker build + Heroku registry as above).

### 2.1 Configuration

From [`config/Config.scala`](https://github.com/gemini-hlsw/lucuma-odb/blob/main/modules/sso-service/src/main/scala/config/Config.scala) and SSO-README:

- `LUCUMA_SSO_ENVIRONMENT` — defaults to `local`. In **local** mode almost everything is hardcoded: random in-memory RSA keypair, port 8080, hostname/cookie domain `local.lucuma.xyz`, DB `postgres://jimmy:banana@localhost:5432/lucuma-sso`. The random keypair means **other services cannot verify local-mode JWTs**, so for a multi-service ephemeral stack run SSO in `staging` mode with your own throwaway GPG keypair.
- Non-local mode requires: `PORT`, `DATABASE_URL`, `GPG_SSO_PUBLIC_KEY`, `GPG_SSO_PRIVATE_KEY`, `GPG_SSO_PASSPHRASE`, `LUCUMA_SSO_COOKIE_DOMAIN`, `LUCUMA_SSO_HOSTNAME`, `LUCUMA_ODB_HOSTNAME`; optional Heroku/Honeycomb blocks. Note `hostname`/scheme are baked into redirect URIs (scheme is forced to `https` in non-local mode — relevant if fronting it with plain HTTP in CI).
- `LUCUMA_ORCID_CLIENT_ID` / `LUCUMA_ORCID_CLIENT_SECRET` are **always required to boot** (all environments, [`OrcidConfig.scala`](https://github.com/gemini-hlsw/lucuma-odb/blob/main/modules/sso-service/src/main/scala/config/OrcidConfig.scala)), but only exercised by the ORCID browser flow — dummy values suffice if you only use guest auth / API keys.

### 2.2 API for getting a JWT without a browser

From [`modules/sso-service/src/main/scala/Routes.scala`](https://github.com/gemini-hlsw/lucuma-odb/blob/main/modules/sso-service/src/main/scala/Routes.scala):

| Endpoint | Auth | Result |
|---|---|---|
| `POST /api/v1/auth-as-guest` | **none** | `201` with a guest-user JWT in the body + http-only refresh cookie. The zero-credential path — ideal for load tests if guest privileges suffice. |
| `POST /api/v1/refresh-token` | session cookie | `200` with a fresh JWT (or `403`) |
| `POST /api/v1/create-api-key?role=<role-id>` | `Authorization: Bearer <standard-user JWT>` | `201` with a long-lived API key |
| `GET /api/v1/exchange-api-key?key=<api-key>` | `Authorization: Bearer <service JWT>` | `200` with a JWT for the key's owner, **valid 3 hours** |
| `GET /auth/v1/stage1?state=<uri>` → `/auth/v1/stage2` | browser | ORCID OAuth redirect flow (standard users only) |
| `GET /auth/v1/set-role?role=<id>` | session cookie | new JWT under another owned role |
| `POST /api/v1/logout` | — | clears cookie |
| `POST /graphql` ([`GraphqlRoutes.scala`](https://github.com/gemini-hlsw/lucuma-odb/blob/main/modules/sso-service/src/main/scala/graphql/GraphqlRoutes.scala)) | JWT | user/role admin API |

- **JWT lifetime is hardcoded to 10 minutes** (`Config.JwtLifetime`, marked `TODO: parameterize`); API-key exchange issues 3-hour JWTs; the `create-jwt` CLI issues 1-hour JWTs.
- **Service/test users without ORCID:** the SSO binary has CLI subcommands ([`Main.scala`](https://github.com/gemini-hlsw/lucuma-odb/blob/main/modules/sso-service/src/main/scala/Main.scala)) — `create-service-user <name>` (prints a service JWT; this is what feeds `ODB_SERVICE_JWT` and ITC's `ODB_SERVICE_JWT`) and `create-jwt <role-id>` (1-hour JWT for an existing user role). In production these are run as one-off Heroku dynos (`heroku run … create-service-user <name>`); in an ephemeral stack you can `docker run <sso-image> create-service-user odb` against the same DB/keys.
- **ORCID is required only for standard-user login.** Standard users can otherwise be fabricated by inserting into the SSO DB or via `create-jwt` once a user/role row exists; guests need nothing at all. Whether ODB features under test are permitted to guests is the main open question below.

## 3. Explore (frontend)

Confirmed: Explore lives in <https://github.com/gemini-hlsw/lucuma-apps> under [`explore/`](https://github.com/gemini-hlsw/lucuma-apps/tree/main/explore); the old <https://github.com/gemini-hlsw/explore> repo is **archived**.

- **Build:** Scala.js linked by sbt (`sbt explore_app/buildJsModule`) then bundled by Vite (`pnpm explore build`) in the `explore-deploy` job of [`.github/workflows/ci.yml`](https://github.com/gemini-hlsw/lucuma-apps/blob/main/.github/workflows/ci.yml). Output is a fully static bundle (a PWA, output dir `explore/heroku/static`).
- **Serving:** deployed from GitHub Actions to **Firebase Hosting**, project `explore-gemini`, hosting targets `explore-gemini-dev` / `explore-gemini-stage` / `explore-gemini-prod` ([`.firebaserc`](https://github.com/gemini-hlsw/lucuma-apps/blob/main/explore/.firebaserc), [`firebase.json`](https://github.com/gemini-hlsw/lucuma-apps/blob/main/explore/firebase.json)). **No Docker image for Explore.** [`explore/HEROKU.md`](https://github.com/gemini-hlsw/lucuma-apps/blob/main/explore/HEROKU.md) describes the older Heroku static-buildpack setup, now retired.
- **Environment selection is runtime, not build-time:** the app fetches `/environments.conf.json` and picks the entry whose `hostName` prefix-matches `location.host`, falling back to `"hostName": "*"` ([`AppConfig.parseConf`](https://github.com/gemini-hlsw/lucuma-apps/blob/main/explore/common/src/main/scala/explore/model/AppConfig.scala)). The shipped [`environments.conf.json`](https://github.com/gemini-hlsw/lucuma-apps/blob/main/explore/common/src/main/public/environments.conf.json) maps `*`→dev (`wss://odb-dev.lucuma.xyz/ws`, `https://sso-dev.gpp.lucuma.xyz`, `https://itc-dev.lucuma.xyz/itc`, prefs `wss://gpp-prefs-dev.lucuma.xyz/v1/graphql`), `explore-test.gemini.edu`→staging, `explore.gemini.edu`→production. Fields per entry: `odbURI` (wss), `odbRestURI`, `preferencesDBURI` (a separate Hasura "prefs" service), `itcURI`, `sso.uri`, `otelEndpoint`.
- **For an ephemeral stack:** build once, serve `explore/heroku/static` with any static server, and overwrite `environments.conf.json` with your throwaway endpoints. Local dev already supports an override file `local.conf.json` (see the `reload-on-environments-change` plugin in [`vite.config.mts`](https://github.com/gemini-hlsw/lucuma-apps/blob/main/explore/vite.config.mts)). Beware the PWA service worker caches the conf (workbox cache `environments-config`) — mostly a browser concern, irrelevant for headless load clients.

## 4. ITC and other sidecar services

- **ITC** (`itc/` in lucuma-odb) is required by ODB (`ODB_ITC_ROOT` has no default). Its config ([`itc/service/.../config/Config.scala`](https://github.com/gemini-hlsw/lucuma-odb/blob/main/itc/service/src/main/scala/lucuma/itc/service/config/Config.scala)): `ITC_PORT`/`PORT`, `REDISCLOUD_URL`/`REDIS_URL` (**Redis required on Heroku dynos; optional otherwise**, used as a `volatile-lru` cache), `ODB_BASE_URL`, `ODB_SERVICE_JWT`, optional TTL/concurrency knobs. Note the ODB↔ITC mutual reference: ODB needs ITC's root, ITC needs ODB's URL + a service JWT. ITC data files come via **git LFS**.
- **obscalc / calibrations** workers reuse the ODB config/DB (extra process types on the same Heroku app); they are separate images but an ephemeral stack can likely omit them unless testing background calculations.
- **resource service** (`resource/` module, port 8484) — new, deployed to `lucuma-resource-*` Heroku apps; not referenced by ODB env config, needed only if Explore/clients call it.

## 5. Reusable dev/CI tooling

- [`docker-compose.yml`](https://github.com/gemini-hlsw/lucuma-odb/blob/main/docker-compose.yml) (repo root, lucuma-odb): single `postgres:15` with SSL on (mounts `test-cert/server.{crt,key}`), user `jimmy`/`banana`, DB `lucuma-odb`; [`docker-init/`](https://github.com/gemini-hlsw/lucuma-odb/tree/main/docker-init) scripts create the `lucuma-sso` DB and apply both migration sets with `psql` at initdb; plus an `adminer` UI on :8686. **It does not run the ODB/SSO/ITC services themselves** — the repo's CI (`build` job of ci.yml) does `docker compose up -d` then runs the sbt test suite (8 shards) in-process against it.
- [`modules/service/src/Dockerfile`](https://github.com/gemini-hlsw/lucuma-odb/blob/main/modules/service/src/Dockerfile): pre-migrated Postgres image for testcontainers — a good trick for fast DB boot in load-test CI.
- [`migration-test.yml`](https://github.com/gemini-hlsw/lucuma-odb/blob/main/.github/workflows/migration-test.yml): restores real Heroku DB backups (dev/staging/production) and replays new migrations — useful pattern for regression testing against realistic data (needs `HEROKU_API_KEY`).
- [`modules/sso-backend-example/`](https://github.com/gemini-hlsw/lucuma-odb/tree/main/modules/sso-backend-example): minimal example of a backend using `lucuma-sso-backend-client` (service JWT + API-key exchange).
- No existing compose file or script boots ODB+SSO+ITC as containers together; that glue (build/pull images, generate GPG keypair, `create-service-user`, wire env vars) is what our system would add.

## Open questions / caveats

1. **No public images.** Verified Docker Hub `noirlab` shows only `gemconda` publicly; GHCR org packages could not be listed without auth (API returns 401) but no workflow pushes there. Pulling `registry.heroku.com/...-dev/web:latest` requires a `HEROKU_API_KEY` with access to the Gemini Heroku apps — need to confirm Carlos's team has (or can get) that; otherwise CI must `sbt docker:publishLocal` (multi-GB build, needs 6GB heap, temurin 25, git-lfs).
2. **Guest-user capability in ODB** — `auth-as-guest` is credential-free, but which ODB GraphQL operations guests may perform (program creation, proposal editing, etc.) was not verified; load tests may need standard users (SSO DB inserts or `create-jwt`).
3. **Standard/test user seeding** — `create-jwt <role-id>` requires an existing user+role row; the exact SQL/GraphQL to fabricate a standard user without ORCID was not traced.
4. **Preferences DB** (`preferencesDBURI`, a Hasura GraphQL service, repo likely `gemini-hlsw/lucuma-prefs` or similar) is required by Explore's conf schema but its deployment was not investigated; unknown whether Explore degrades gracefully without it.
5. **`otelEndpoint` in Explore conf** is `Option`al (decoder tolerates `null`/absent) — fine to omit in a throwaway conf.
6. **SSO scheme hardcoding**: non-local SSO forces `https` in its public URI; running SSO behind plain HTTP in CI may break the cookie/redirect flow (guest auth via direct POST probably still works — unverified). Cookie is http-only and scoped to `LUCUMA_SSO_COOKIE_DOMAIN`.
7. **10-minute JWT lifetime is hardcoded** in SSO — long load-test runs must refresh via the cookie or re-exchange API keys.
8. **`vars.HEROKU_*_APP_NAME` overrides** in ci.yml suggest forks deploy to differently-named Heroku apps; defaults (`lucuma-postgres-odb`, `lucuma-sso`, `itc`, `lucuma-resource`) are the Gemini ones.
9. **obscalc/calibrations necessity**: whether ODB responses awaited by Explore (e.g. execution digests) require the obscalc worker to be running was not verified.
10. Heroku "release phase" behavior (whether Heroku runs a release command besides the in-app Flyway) was not checked; no `Procfile`/`heroku.yml` exists in the repo, so startup-time Flyway appears to be the only migration mechanism.
